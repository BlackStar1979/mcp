## 6. Poważne problemy i ryzyka

### 6.1 Dokumentacja jest bardziej chaotyczna niż kod

To jest dziś najważniejszy problem projektu.

Kod:

- ma już dość czytelny baseline runtime,
- ma testy,
- ma local control plane,
- ma oddzielony safe profile.

Dokumentacja:

- miesza current state, roadmapę, research, incident notes, next-session memory i timeline,
- ma zbyt wiele top-level dokumentów o podobnej randze,
- nie oznacza jasno świeżości i autorytetu każdego pliku,
- zostawia czytającego z fałszywym wrażeniem, że "wszystko jest runtime truth".

### 6.2 `code_tools.js` pozostaje trwałym źródłem regresji

Pełny `core/code_tools.js` nadal:

- istnieje w repo,
- zawiera patch, rollback, dispatch i execution surface,
- jest niebezpieczny dla connector-safe exposure.

To nie jest problem aktywnego runtime dziś, ale to jest stale obecne ryzyko regresji.

### 6.3 `REGISTRY_RUNTIME_DESIGN.md` łączy design i wdrożone milestones

Ten plik jest wartościowy, ale niebezpieczny jako samodzielne źródło prawdy, bo jednocześnie:

- opisuje projekt v1 jako design baseline,
- opisuje kolejne milestone jako wdrożone,
- kończy się kandydatem v7.

Czytelnik bez kontekstu nie odróżni łatwo:

- co jest projektem,
- co już żyje w runtime,
- co jest kolejnym planem.

### 6.4 `MCP_INTEGRATION_ISSUES.md` miesza normy i incydenty

To cenny dokument, ale zawiera obok siebie:

- reguły runtime,
- lekcje po dawnych błędach,
- nowe incydenty patch/deploy,
- status registry milestones.

Skutek:

- plik jest dobry jako pamięć problemów,
- zły jako czysty opis aktualnego systemu.
